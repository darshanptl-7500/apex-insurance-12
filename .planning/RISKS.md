# Apex Insurance — Risk & Technical Debt Register

> Generated by `/rapidx:onboard-codebase` from a codebase scan on 2026-08-13. Re-run `/rapidx:scan` or `/rapidx:map-codebase` periodically to keep this current.

Severity is scored for **"if this repo/app were ever exposed beyond a local demo"** — several items are acceptable for a sandboxed training app but become critical the moment this touches a shared environment, a real database, or the public internet.

## Critical

### 1. Live-looking SQL Server credentials committed to source
- **Where:** `src/ApexInsurance.Api/appsettings.json:3`
- **What:** A full Azure SQL connection string with a real-looking `User ID` / `Password` is committed to the repo. `README.md:59` explicitly acknowledges this: *"Rotate the SQL credentials in `appsettings.json` if this repo is shared; they were carried forward from the legacy `Web.config`."*
- **Why it matters:** Secrets in git history persist even after rotation/removal; if this string is (or was) a real, reachable database, it's a live exposure.
- **Fix direction:** Rotate the credential immediately if it is/was live. Move to environment variables / a secrets manager (Key Vault, User Secrets for local dev). Scrub from git history if genuinely sensitive. The `secret-scanner` hook installed by RapidX will flag new instances of this pattern going forward — consider running it retroactively.

### 2. Authentication is not real token security
- **Where:** `src/ApexInsurance.Security/DemoTokenService.cs:17-55`
- **What:** Bearer "tokens" are unsigned Base64-encoded JSON (`{"UserId":...,"Username":...,"Role":...,"Exp":...}`) — there is no HMAC/JWT signature validation anywhere in the codebase.
- **Why it matters:** Anyone can forge a token for any user/role by hand-crafting and base64-encoding JSON, bypassing `AuthorizeRoleAttribute` role checks entirely.
- **Fix direction:** Replace with real signed JWTs (the config even has an unused `Apex:Auth:TokenSigningKey` placeholder in `appsettings.json:12` — wire it up or remove it to avoid the false impression that it does something).

### 3. Bearer token accepted via query string
- **Where:** `ApexInsurance.Api` — `CurrentUserContext.TryExtractBearerToken`
- **What:** Accepts the token via `?access_token=` query parameter in addition to the `Authorization` header.
- **Why it matters:** Tokens in URLs leak via server logs, browser history, and `Referer` headers.
- **Fix direction:** Remove query-string token support; require the `Authorization: Bearer` header only.

### 4. Demo password fallback baked into the real auth code path
- **Where:** `src/ApexInsurance.Services/Auth/AuthService.cs:14-17,49-51`
- **What:** Any seeded user without a stored password hash silently accepts the hardcoded literal `Password1!` (`DemoPassword` const).
- **Why it matters:** This is a backdoor if the code path is ever carried into a non-demo environment without removal — it's easy to forget it's there.
- **Fix direction:** Gate the fallback behind an explicit `Environment.IsDevelopment()` check (or remove entirely) and log loudly if it's ever exercised outside dev.

## High

### 5. No CI/CD automation
- **What:** No `.github/workflows`, `azure-pipelines.yml`, or `Jenkinsfile` anywhere in the repo. The xUnit unit tests and Playwright E2E suite (60 tests, well-aligned with `docs/E2E-TEST-CASES.md`) never run automatically.
- **Why it matters:** Regressions can land on `main` undetected; the good test coverage that exists provides no safety net without automation.
- **Fix direction:** Add a basic pipeline (build → `dotnet test` → `playwright test`) — GitHub Actions is the natural fit given no other CI is configured.

### 6. Stale/misleading schema-management comment
- **Where:** `database/01_CreateSchema.sql:1` — `/* Apex Insurance — schema matching EF6 ApexInsuranceDbContext (plural tables) */`
- **What:** The comment says "EF6" but every project targets `net10.0` with `Microsoft.EntityFrameworkCore.SqlServer` 10.0.0 (EF Core), and there is no EF Core `Migrations/` folder — the schema is entirely hand-maintained via the SQL scripts in `database/`.
- **Why it matters:** Misleads new contributors (and AI agents) into thinking EF migrations manage the schema, or that this is a legacy EF6 app.
- **Fix direction:** Fix the comment; document clearly (in `.planning/PROJECT.md` or a README note) that schema changes must be made by hand-editing the `database/*.sql` scripts, since there's no code-first migration path.

### 7. Thin unit test coverage on business logic
- **What:** Only 2 unit test files (`UwStructureSmokeTests.cs`, `SecurityAndSharedSmokeTests.cs`), 8 total test cases — smoke-level only. Rating, authority/referral rules, pipeline, and workflow logic have no unit-level coverage; correctness currently relies entirely on the Playwright E2E suite.
- **Fix direction:** Add unit tests for `RatingService`, authority/referral rule evaluation, and workflow state transitions before making non-trivial changes there — these are exactly the modules flagged as high-coupling "hub modules" in the knowledge graph.

## Medium

### 8. All demo accounts share one well-known password
- **Where:** `database/02_SeedData.sql`, `database/04_DemoBrokerOpsUser.sql`, `README.md:78-85`
- **What:** Seeded users (`admin`, `uw1`, `mgr1`, `cl1`, `bro1`, …) have `NULL` password hashes and rely entirely on the `AuthService` demo fallback (risk #4) with password `Password1!`.
- **Fix direction:** Call out explicitly (README + RISKS) that these seed scripts must never be run against a real/production database.

### 9. No security documentation or organizational mandates on file
- **What:** `/rapidx:learn --security` and `--mandates` found no `SECURITY.md`, threat model, CODEOWNERS, Dependabot, Semgrep/CodeQL config, or `.env.example`; no org policy/mandate docs exist in `.rapidx/inputs/`.
- **Why it matters:** RapidX's governance hooks (`secret-scanner`, `audit-trail`, `invariant-check`) are running with no project-specific rules layered on top — only generic defaults.
- **Fix direction:** If this project is meant to model a regulated insurance carrier's standards, drop policy/security docs into `.rapidx/inputs/` and re-run `node scripts/learn-codebase.js --mandates --security`, then generate invariants with `/rapidx:invariant-catalog --from-knowledge`.

### 10. No architecture decision records
- **What:** No ADRs, no `ARCHITECTURE.md`. The layered dependency structure and the Open-Box-as-stub design are currently only discoverable by reading code and `docs/UW-SOLUTION-MAP.md`.
- **Fix direction:** Capture at least one ADR for "Open Box is a local stub, not a real integration" and one for "schema is SQL-script-managed, not EF-migration-managed" — both are non-obvious and easy for a new contributor (or agent) to get wrong. Use `/rapidx:adr`.

## Low / informational

- **"OpenBox" naming is intentional, not legacy cruft** — `ApexInsurance.Data.OpenBox` is a deliberate stub of a fictional legacy policy admin system (`LocalOpenBoxGateway`, `OpenBoxIntegrationBus`), confirmed by `docs/UW-SOLUTION-MAP.md`. Worth a one-line note in onboarding docs so nobody "fixes" it into a real integration by mistake.
- **RabbitMQ is optional and demo-scoped** — gated by `Apex:RabbitMQ:Enabled`; both hosted consumers no-op gracefully when disabled/unreachable. Default `guest`/`guest` credentials (`appsettings.json:23-24`, `appsettings.Development.json:14`) are fine for a local broker but must not be reused if RabbitMQ is ever exposed beyond localhost.
- **No linting/formatting config detected** (no ESLint/Prettier/.editorconfig) — low risk, but worth adding for consistency as the Angular/AngularJS frontend grows.
- **Angular 8.2.14 is well past EOL** — no immediate risk in a demo, but any real modernization effort should plan an Angular upgrade path (8 → current) alongside eventually retiring the AngularJS shell.

1. Treat items 1–4 as blocking if this app is ever pointed at a real database or exposed outside localhost.
2. Run `/rapidx:invariant-catalog --from-knowledge` to turn items 1, 2, 3, and 8 into enforced, always-on checks rather than one-time notes.
3. Add CI (item 5) before making further changes, so the existing test suites start providing real regression protection.
